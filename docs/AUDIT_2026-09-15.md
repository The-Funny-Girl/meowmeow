# Kirkware Linux runtime audit — 2026-09-15

This audit covers the supported/private Garry's Mod test path, desktop control UI, profile bridge, and cooperative load harness. It does not cover arbitrary-process injection.

## Confirmed findings

1. **Sandbox team filtering can hide all aim targets.** `kirkware_linux_combat.lua` rejects matching team IDs when `kirkware_aim_teammates=0`. Plain Sandbox players can share `TEAM_UNASSIGNED`, so a private Sandbox test may have no eligible target. Short-term test workaround: enable **Aim at teammates**. Preferred fix: only apply same-team rejection when the team is a real assigned team rather than `TEAM_UNASSIGNED`/0.

2. **Desktop test target lifecycle leak.** `kirkware-control-ui.py` can start `kirkware-load-target`, but closing the Tk UI does not stop that child. This can leave a stale cooperative target/control directory for a later run. Preferred fix: on UI close, stop only the `Popen` child owned by that UI, first through the cooperative quit command and then with a bounded terminate fallback.

3. **Profile writes are non-atomic.** The desktop UI writes `desktop_profile.conf` directly while the Lua bridge polls it. A read during truncate/write can observe a partial profile. Preferred fix: write a temporary file in the same directory and atomically replace the destination.

4. **Profile numeric values are not independently validated by the bridge.** The UI spinboxes have ranges, but imported/edited profile files can contain invalid numeric strings. The bridge currently forwards allowlisted values with `RunConsoleCommand`. Preferred fix: validate numeric type and clamp to the same declared bounds before applying.

5. **Existing-running-game / log rotation edge case.** The private-test launcher rotates `garrysmod/console.txt` before starting GMod. If GMod is already running, the existing process can keep the old file descriptor and make verification misleading. Preferred fix: refuse to start the isolated test while an existing GMod process is active, or explicitly require an override.

6. **Game-directory discovery is inconsistent.** The desktop UI knows native Steam, Debian-installation, Flatpak, and Snap paths, while the installer/launcher/verifier do not all share the same set. Preferred fix: centralize discovery or at least align all candidate paths.

7. **The verifier proves initialization, not gameplay correctness.** `verify-gmod-live-test.sh` checks module startup log lines. That is useful but does not prove target acquisition, ESP drawing, movement correction, or other feature behavior. Runtime diagnostics should report live module/convar state and a private multi-client test should be used for behavior.

## Safe native-loading direction

For native code inside Garry's Mod, prefer the documented Garry's Mod binary-module mechanism: install a platform/realm-specific module under `garrysmod/lua/bin/` and load it with Lua `require()`. Keep the current folder addon for configuration/UI and private test orchestration. The cooperative `.so` harness remains useful for standalone controlled targets, not for attaching to unrelated running processes.
